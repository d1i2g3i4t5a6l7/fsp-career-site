# Платформа ФСП: архитектура сервисов и подход

Oct 6, 2026 · @Cena

## Подход кратко

Платформа подтверждает грейд кандидата рабочими задачами с разрешённым ИИ, а работодатель находит кандидатов по подтверждённому профилю и сам выходит на контакт. Все модели — национальные, поколение GigaChat 3.x: флагман GigaChat 3.5 Ultra через OpenAI-совместимый API cloud.ru и открытая GigaChat 3.1 Lightning на своём сервере. Сервисы обращаются к ним только через один LLM-шлюз.

1. **Банк задач с приёмкой.** Задачу пишет эксперт или работодатель либо генерирует GigaChat по шаблону и вакансии. В банк она попадает после пяти проверок; решающие из них — прогон агента без человека (он не должен пройти) и решение экспертом в лимит времени (он должен успеть).
2. **Грейд подтверждается двумя задачами.** Кандидат решает две задачи разных типов заявленного уровня во встроенной среде: ассистент на GigaChat, бот-«заказчик» и песочница для кода. Сессия пишется автоматически. LLM-оценщик ставит «да/нет» по каждому критерию рубрики с цитатой, в трёх прогонах.
3. **Фидбэк собирается из оценки, а не заново.** Рекомендации кандидату и отчёт работодателю строятся только из засчитанных и незасчитанных критериев: без новых суждений и без раскрытия эталона.
4. **Профиль кандидата — это грейд, навыки и домены.** Навыки подтверждаются тегами засчитанных критериев, домены — опытом, задачами и ФСП. Граф смежности переносит опыт между близкими доменами без изменения грейда: Senior в CV остаётся Senior и попадает в выдачу NLP-позиции с пометкой «смежный домен» и более низким соответствием, чем кандидат с опытом в NLP.
5. **Два канала контакта, одно ранжирование.** Работодатель ищет по потребности или в банке кандидатов и отправляет приглашение с вилкой; кандидат может откликнуться на вакансию сам. В обе стороны работает один и тот же расчёт соответствия.

Документ описывает только модели и бэкенд; фронтенд — за рамками.

## Набор сервисов

Сервисы разбиты на три домена — «Кандидат и профиль», «Оценка», «Найм» — и общую инфраструктуру. Синхронные вызовы идут через API Gateway, долгие операции (оценка, приёмка задач, эмбеддинги) — через очередь событий.

> Схема: карта сервисов · 3 домена, 15 сервисов, общая инфраструктура — смотреть в [живом документе](https://claude.ai/code/artifact/7247b966-df2c-4f73-a667-7e66f4f5802c)

LLM Gateway выделен: к GigaChat обращается только он, поэтому лимит потоков, токен и учёт расходов живут в одном месте.

| Сервис | Домен | Отвечает за | Модель |
| --- | --- | --- | --- |
| API Gateway | — | Вход для фронта: проверка JWT, маршрутизация, лимиты запросов | — |
| Identity (Keycloak) | Профиль | Регистрация, подтверждение email, роли, привязка ФСП ID | — |
| Profile | Профиль | Профиль, разбор PDF-резюме, опыт по доменам, согласия, PDF-профиль | GigaChat 3.1 Lightning |
| Taxonomy | Профиль | Специализации, грейды, навыки, домены, граф смежности с весами | — |
| FSP Adapter | Профиль | Достижения из реестра ФСП | — |
| Task Bank | Оценка | Шаблоны, задачи, рубрики, версии и статусы | GigaChat 3.5 Ultra |
| Task QA | Оценка | Приёмка задачи: автопроверки, агент без человека, экспертное решение | GigaChat 3.5 Ultra, 3.1 Lightning |
| Assessment | Оценка | Подбор задач, попытки, таймер, правила грейда, кулдауны | — |
| Workspace | Оценка | Встроенный ассистент, бот-«заказчик», журнал сессии | GigaChat 3.5 Ultra, 3.1 Lightning |
| Sandbox Runner | Оценка | Исполнение кода и тестов в контейнере без сети | — |
| Grading | Оценка | LLM-оценщик по рубрике: 3 прогона, проверка цитат | GigaChat 3.5 Ultra |
| Feedback | Оценка | Рекомендации кандидату и отчёт работодателю | GigaChat 3.5 Ultra |
| Matching | Найм | Разбор позиций, эмбеддинги, мэппинг, ранжирование, объяснения | GigaChat 3.1 Lightning, EmbeddingsGigaR |
| Vacancies | Найм | Вакансии и отклики кандидатов | GigaChat 3.1 Lightning |
| Drafting | Найм | Приглашения, квоты, статусы | — |
| Notifications | Найм | Письма о статусах | — |
| LLM Gateway | Инфраструктура | Единственная точка к моделям: маршрутизация по каналам (cloud.ru, свой vLLM, API Сбера), очередь, схемы ответа, учёт токенов, реестр промптов | все |

Хранилища: PostgreSQL с pgvector (данные и векторы), Valkey (очереди, события, кэш), S3-совместимое хранилище (материалы задач, журналы сессий, PDF).

**На хакатоне** логические сервисы собираются в пять контейнеров, чтобы не тратить время на сеть между ними:

1. **core-api** — модульный монолит: Profile, Taxonomy, Task Bank, Assessment, Matching, Vacancies, Drafting, FSP Adapter.
2. **ai-worker** — фоновые задачи: Task QA, Grading, Feedback, пересчёт эмбеддингов.
3. **workspace** — WebSocket-сессии кандидата: ассистент, «заказчик», журнал.
4. **llm-gateway** — отдельно, потому что все остальные делят его лимит потоков.
5. **runner** — песочница для кода.

Плюс Keycloak, PostgreSQL, Valkey и vLLM с GigaChat 3.1 Lightning — ему нужна видеокарта; без неё сценарии Lightning временно уходят в GigaChat 3.5 Ultra через cloud.ru. Границы модулей внутри core-api совпадают с сервисами из таблицы, поэтому разнести их позже — механическая работа.

## Сценарий 1. Добавление задачи в банк

Задача проходит одинаковый конвейер, откуда бы она ни пришла: своя от эксперта или работодателя либо сгенерированная GigaChat. Опубликованной она становится, только если агент без человека её не проходит, а эксперт решает в лимит времени.

> Схема: приёмка задачи · 2 входа, 5 проверок, 2 решения — смотреть в [живом документе](https://claude.ai/code/artifact/7247b966-df2c-4f73-a667-7e66f4f5802c)

Любой провал — автопроверки, агент, эксперты или дрейф уже опубликованной задачи — возвращает её на доработку, а правка создаёт новую версию.

### Два входа

- **Своя задача.** Автор загружает условие, материалы (репозиторий, данные, логи) и эталонное решение. Недостающее — рубрику, скрытые факты «заказчика», лимит времени — Task Bank предлагает сгенерировать по шаблону типа, автор правит.
- **Генерация через ИИ.** Автор выбирает тип (баг, дизайн, фича по абстрактному ТЗ), уровень, специализацию и домен, прикладывает вакансию или потребность. GigaChat 3.5 Ultra по шаблону выдаёт черновик в строгой JSON-схеме: условие, видимые ограничения, скрытые факты для «заказчика», эталон, критерии рубрики с весами и тегами навыков, лимит времени.
- **Задачи на поиск бага** собираются в два шага: модель пишет корректный код с тестами, затем вносит дефект заданного класса (гонка, N+1, утечка ресурса). Песочница проверяет, что до внесения тесты проходят, а после — падают.

### Пять проверок

| Проверка | Кто делает | Критерий прохождения |
| --- | --- | --- |
| 1. Структура | Task QA, правила + GigaChat 3.1 Lightning | Все поля заполнены; каждое скрытое ограничение покрыто хотя бы одним критерием; критерии проверяют решения, а не наличие разделов; нет противоречий в условии |
| 2. Исполнимость | Task QA + Sandbox Runner | Материалы собираются, эталон проходит скрытые тесты, дефект в задаче на баг воспроизводится |
| 3. Агент без человека | Task QA, GigaChat 3.5 Ultra с функциями `run_code` и `ask_customer` | В трёх прогонах в лимите времени агент набирает меньше порога уровня задачи |
| 4. Калибровка оценщика | Task QA + Grading | Эталон получает высокий балл, автоматически ухудшенные решения — низкий; разброс трёх прогонов в пределах нормы |
| 5. Экспертное решение | 1–2 эксперта платформы в Workspace | Медиана времени — в лимите; эксперт отмечает критерии, обязательные для каждого грейда, — так задаются пороги |

Провал любой проверки возвращает задачу автору с причиной. Типовая правка после проверки 3 — добавить ограничение, которое открывается только по вопросу «заказчику».

### Статусы задачи

черновик → на приёмке → опубликована → снята. Любая правка опубликованной задачи создаёт новую версию и заново проходит проверки 3–5. Снимаем задачу, когда доля решивших заметно растёт без изменения состава кандидатов (признак утечки) или когда новая модель GigaChat проходит её без человека.

### API и события

| Вызов | Назначение |
| --- | --- |
| `POST /tasks` | Своя задача; поля, которых нет, — `generate: true` |
| `POST /tasks/generate` | Черновик по типу, уровню, домену и вакансии |
| `POST /tasks/{id}/submit` | Отправить на приёмку → событие `task.qa_requested` |
| `GET /tasks/{id}/qa` | Результаты пяти проверок |
| `POST /tasks/{id}/expert-runs` | Сессия эксперта в Workspace |

События: `task.qa_requested`, `task.qa_failed`, `task.published`, `task.retired`.

## Сценарий 2. Регистрация и подтверждение грейда

Грейд подтверждается двумя задачами разных типов заявленного уровня; сессия решения пишется автоматически, оценка идёт асинхронно. Профиль кандидата собирается по ходу: резюме даёт опыт и домены, задачи — подтверждённые навыки.

> Схема: подтверждение грейда · 8 шагов, 1 решение, 2 петли — смотреть в [живом документе](https://claude.ai/code/artifact/7247b966-df2c-4f73-a667-7e66f4f5802c)

В каждом шаге указан сервис, который его выполняет; петля слева — вторая задача, петля справа — переход на уровень ниже без понижения грейда.

### Шаги

1. **Регистрация.** Identity (Keycloak): email с подтверждением или вход через ФСП ID. Два согласия по 152-ФЗ — на обработку и на показ профиля работодателям.
2. **Профиль из резюме.** Profile отправляет текст PDF в GigaChat 3.1 Lightning со строгой JSON-схемой: места работы с периодами, роли, стек, домены проектов, софт-скиллы. Кандидат проверяет и правит разбор. Навыки из резюме получают статус «заявлен».
3. **Опрос и заявленный грейд.** Направление → специализация → стек → домены → формат → вилка. Taxonomy нормализует навыки и домены через словарь синонимов.
4. **Подбор задач.** Assessment выбирает две задачи разных типов уровня заявленного грейда: по специализации, с приоритетом стека и доменов кандидата, исключая уже решённые им задачи и выравнивая частоту показа задач.
5. **Решение.** Workspace открывает сессию с таймером. Внутри — ассистент на GigaChat 3.5 Ultra, бот-«заказчик» и песочница. Каждое событие пишется в журнал: запросы к ассистенту и ответы, вопросы «заказчику», правки кода, запуски тестов.
6. **Оценка.** После сдачи событие `attempt.submitted` → Grading: три независимых прогона оценщика по рубрике, по каждому критерию «да/нет» с цитатой из решения или журнала. Критерий без найденной цитаты не засчитывается. Итог — взвешенная сумма; при расхождении прогонов берётся нижний балл.
7. **Вторая задача** — тот же цикл.
8. **Решение о грейде.** Подтверждён, если обе задачи не ниже порога уровня. Не подтверждён — сразу доступны задачи уровнем ниже; на тот же уровень — через 30 дней. Смена подтверждённого грейда — не чаще раза в 90 дней.
9. **Профиль в поиске.** Событие `grade.confirmed` → Profile отмечает навыки по тегам засчитанных критериев как «подтверждён», добавляет домены решённых задач, Matching пересчитывает эмбеддинг профиля и включает кандидата в выдачу.

### Что видит кандидат во время ожидания

Оценка занимает минуты, а не секунды: три прогона на GigaChat 3.5 Ultra через очередь шлюза. Поэтому статус попытки — «на проверке», уведомление приходит, когда готов фидбэк (сценарий 3).

### API и события

| Вызов | Назначение |
| --- | --- |
| `POST /profile/resume` | Загрузка PDF → разобранные поля для проверки |
| `PUT /profile/survey` | Опрос и заявленный грейд |
| `POST /assessment/plan` | Подбор двух задач под заявленный грейд |
| `POST /attempts/{id}/start` · `WS /workspace/{attemptId}` | Старт и сессия решения |
| `POST /attempts/{id}/submit` | Сдача → `attempt.submitted` |
| `GET /assessment/status` | Попытки, баллы, решение о грейде, даты кулдаунов |

События: `attempt.submitted`, `grading.completed`, `grade.confirmed`, `grade.not_confirmed`.

## Сценарий 3. Фидбэк кандидату и отчёт работодателю

Оба текста собираются из одних и тех же фактов — вердиктов оценщика по критериям и журнала сессии. Модель только переводит факты на человеческий язык; новых оценок она не выносит, поэтому фидбэк не может разойтись с баллом.

> Схема: фидбэк · 3 источника фактов, 2 текста, 1 проверка — смотреть в [живом документе](https://claude.ai/code/artifact/7247b966-df2c-4f73-a667-7e66f4f5802c)

Проверка опоры на факты общая для обоих текстов: пункт без ссылки на критерий отбрасывается, а текст с большой долей таких пунктов генерируется заново.

### Шаги

1. **Сборка фактов.** По событию `grading.completed` Feedback собирает по каждому критерию: итог «да/нет», цитату, вес, теги навыков, тип критерия (решение или процесс). Из журнала — сводку процесса: сколько вопросов задано «заказчику», были ли отклонены предложения ассистента, запускались ли тесты.
2. **Генерация двух текстов** — GigaChat 3.5 Ultra, строгая JSON-схема, где каждый пункт обязан ссылаться на `criterion_id`.
3. **Проверка опоры на факты.** Пункт без ссылки или со ссылкой на критерий с другим итогом отбрасывается; если отброшено больше трети — перегенерация.
4. **Публикация.** Рекомендации — в кабинет кандидата; отчёт — в карточку кандидата для работодателя, в подборке и в откликах.

### Что получает каждая сторона

|  | Кандидат | Работодатель |
| --- | --- | --- |
| Сильные стороны | Засчитанные критерии и почему это важно | Что кандидат сделал — человеческим языком |
| Пробелы | Незасчитанные критерии как навыки для развития: «проверяйте ограничения по данным до выбора архитектуры» | Что не сделал, с весом: «не учёл ограничение по приватности — важный пробел для этой роли» |
| Работа с ИИ | Где принял неверное предложение ассистента | Проверял ли вывод ИИ, задавал ли уточняющие вопросы |
| Чего нет | Эталона и прямого ответа на задачу | Текста задачи и решения |

Запрет на эталон в фидбэке кандидату — защита банка: иначе разбор задачи разойдётся между кандидатами. Рекомендация формулируется на уровне навыка или принципа, а не конкретного ответа.

### Для задач работодателя

Если задачу прислал сам работодатель (поиск через задачу), он видит полный отчёт и само решение кандидата — задача его, утечки нет. Кандидат получает тот же разбор, что и обычно.

### API и события

| Вызов | Назначение |
| --- | --- |
| `GET /attempts/{id}/feedback` | Рекомендации для кандидата |
| `GET /candidates/{id}/report` | Отчёт для работодателя по всем задачам кандидата |

Событие: `feedback.ready` → Notifications.

## Сценарий 4. Отклик на вакансию

Отклик — зеркало поиска: вакансия разбирается в ту же «позицию», что и потребность работодателя, и Matching считает то же соответствие M, только со стороны кандидата. Откликаться может кандидат хотя бы с одним подтверждённым грейдом — так работодатель получает отклики с той же проверенной карточкой, что и в подборке.

1. **Публикация вакансии.** Vacancies проверяет вилку: «от» не больше «до», ширина не больше 40% нижней границы. GigaChat 3.1 Lightning разбирает текст в позицию: специализация, домен, окно грейда, обязательные и желательные навыки, требуемый опыт в домене. Работодатель подтверждает разбор. Matching считает эмбеддинг позиции (EmbeddingsGigaR).
2. **Лента вакансий для кандидата.** Matching отбирает вакансии в категории кандидата и в смежных доменах (сценарий 5) и сортирует по M. У каждой — объяснение: «ваш грейд Middle подтверждён, вакансия ждёт Senior — отклик возможен, шансы ниже».
3. **Отклик.** Не больше 20 откликов в неделю. Отклик сохраняет снимок карточки кандидата и M на момент отклика — работодатель видит то, на основании чего кандидат откликнулся.
4. **Сторона работодателя.** Отклики отсортированы по M, к каждому — отчёт из сценария 3. Контакты откликнувшегося видны сразу, как требует ТЗ.
5. **Статусы.** Отправлен → просмотрен → приглашение на интервью или отказ с причиной из списка. Обе стороны видят текущий статус; Notifications шлёт письмо при каждом переходе.

| Вызов | Назначение |
| --- | --- |
| `POST /vacancies` | Публикация, ответ — разобранная позиция для подтверждения |
| `GET /vacancies/feed` | Лента для кандидата, сортировка по M |
| `POST /vacancies/{id}/applications` | Отклик (лимит в неделю) |
| `GET /vacancies/{id}/applications` | Отклики для работодателя с отчётами |
| `PATCH /applications/{id}` | Смена статуса |

События: `vacancy.published`, `application.created`, `application.status_changed`.

## Сценарий 5. Поиск кандидатов и мэппинг

Кандидат и позиция приводятся к одной модели: специализация, грейд, навыки, домены, опыт. Граф смежности позволяет искать за пределами точного домена; грейд кандидата при этом не меняется — смежность влияет только на соответствие позиции.

### Профиль кандидата

| Часть | Откуда берётся | Чем подтверждается |
| --- | --- | --- |
| Специализация и грейд | Только из задач | Две задачи разных типов не ниже порога уровня |
| Навыки | Резюме, опрос, задачи | «Подтверждён» — тег засчитанного критерия; «заявлен» — только резюме или опрос |
| Домены (CV, NLP, финтех, e-commerce…) | Опыт, задачи, ФСП | Сила доказательства: задача в домене > опыт в годах > дисциплина ФСП > упоминание в резюме |
| Опыт | Резюме | Годы общие, по специализации и по каждому домену |

Если грейд подтверждён задачами, а опыт сильно меньше типичного для грейда, кандидат получает пометку «грейд подтверждён задачами, опыт меньше типичного». Это информация для работодателя, а не блокировка: задачи весят больше стажа.

### Позиция

Потребность работодателя или вакансия разбирается GigaChat 3.1 Lightning в одну и ту же структуру: специализация, домен, окно грейда, обязательные и желательные навыки, требуемые годы опыта в домене, формат, вилка. Работодатель видит разбор и правит его.

### Граф смежности

Узлы — специализации, домены и навыки, рёбра — вес переносимости опыта w от 0 до 1. Стартовые веса задают эксперты (GigaChat предлагает кандидатов в рёбра по совместной встречаемости в резюме и вакансиях); после запуска веса дообучаются на исходах: принятые приглашения и подтверждённые на собеседовании уровни.

> Схема: граф смежности ML-доменов · стартовые веса — смотреть в [живом документе](https://claude.ai/code/artifact/7247b966-df2c-4f73-a667-7e66f4f5802c)

Веса на рёбрах — стартовые, их задают эксперты; ребро CV–NLP выделено, потому что на нём построен пример ниже.

| Пара | Стартовый w | Что переносится |
| --- | --- | --- |
| NLP ↔ LLM-инженерия | 0,8 | Трансформеры, токенизация, оценка текстовых моделей |
| CV ↔ NLP | 0,6 | Основа глубокого обучения: PyTorch, обучение и оценка моделей |
| NLP ↔ Speech | 0,6 | Работа с последовательностями |
| Backend ↔ Fullstack | 0,8 | Серверная часть целиком |
| Frontend ↔ Fullstack | 0,7 | Клиентская часть целиком |
| Классический ML ↔ CV | 0,4 | Постановка задачи и метрики, но не архитектуры |
| Data Analyst ↔ ML Engineer | 0,4 | Работа с данными и метриками |

| Вес ребра | Как смежный кандидат попадает в выдачу |
| --- | --- |
| ≥ 0,5 | В основную выдачу с пометкой «смежный домен»; слагаемое «Домен» в M равно весу ребра |
| < 0,5 | Только при включённом «широком поиске» |

Грейд при этом не меняется: Senior в CV остаётся Senior и на NLP-позиции. Инженерный уровень переносится между доменами, а нехватка доменного опыта видна работодателю отдельно — в соответствии M и в объяснении. Так же со смежными специализациями: подтверждённый грейд остаётся, кандидат помечается «смежная специализация». Решённая задача в целевом домене поднимает слагаемое «Домен» до 1, поэтому задача от работодателя — короткий путь для смежного кандидата наверх подборки.

### Алгоритм мэппинга

> Схема: конвейер мэппинга · 3 пути отбора, 4 шага — смотреть в [живом документе](https://claude.ai/code/artifact/7247b966-df2c-4f73-a667-7e66f4f5802c)

Три пути отбора работают параллельно и сливаются до жёстких фильтров; смежный домен понижает только слагаемое «Домен» в соответствии, грейд кандидата остаётся подтверждённым.

1. **Нормализация.** Навыки и домены кандидата и позиции приводятся к узлам таксономии через словарь синонимов.
2. **Отбор тремя путями.** Точная категория; смежные по графу с весом от 0,5; векторный поиск по эмбеддингам EmbeddingsGigaR в pgvector (топ-200) — ловит профили, которые словарь не распознал.
3. **Жёсткие фильтры.** Окно активности, формат, вилка (ожидания кандидата не выше верхней границы более чем на 25%), блок-лист компаний кандидата, окно грейда: подтверждённый грейд от уровня позиции до ступени выше, на ступень ниже — по галочке.
4. **Соответствие домена.** 1, если у кандидата есть опыт или решённая задача в домене позиции; иначе — вес ребра от его ближайшего домена, умноженный на силу доказательства.
5. **Релевантный опыт.** Годы в целевом домене плюс годы в смежных доменах, умноженные на вес ребра; соответствие опыту — их отношение к требуемому, не больше 1.
6. **Ранжирование.** Соответствие M с двумя новыми слагаемыми — домен и опыт.
7. **Объяснение** из вкладов слагаемых.

```latex
M = 0{,}30\,\text{Стек} + 0{,}20\,\tfrac{S}{100} + 0{,}15\,\text{Домен} + 0{,}10\,\text{Опыт} + 0{,}10\,\text{Смысл} + 0{,}10\,\text{Зарплата} + 0{,}05\,\text{Доступность}
```

«Домен» — максимум по доменам кандидата из силы доказательства, умноженной на вес ребра до домена позиции. Остальные слагаемые — как в основном документе.

### Пример: позиция NLP Middle, от 2 лет в NLP

| Кандидат | Путь отбора | Грейд | Домен в M | Релевантный опыт | Итог |
| --- | --- | --- | --- | --- | --- |
| Middle NLP, 3 года в NLP | Точная категория | Middle | 1 | 3 года | Выше всех |
| Senior CV, 5 лет в CV | Смежный, вес 0,6 | Senior, в окне позиции | 0,6 | 0,6 × 5 = 3 года | В выдаче с пометкой «смежный домен», ниже первого |
| Middle CV, 2 года в CV | Смежный, вес 0,6 | Middle | 0,6 | 1,2 года из 2 | В выдаче, ниже второго |

Объяснение для второго кандидата: «Senior подтверждён; CV → NLP — смежный домен, вес 0,6; PyTorch и обучение моделей подтверждены; опыт в NLP — 0 лет».

### Фильтры позиции

Фильтры не задаются вручную с нуля, а заполняются из позиции: специализация; домен и переключатель «смежные домены»; окно грейда; минимум релевантного опыта; обязательные навыки и переключатель «только подтверждённые»; достижения ФСП; формат; вилка. Любая правка создаёт новую версию подборки. Подсказки «что ослабить» считаются повторным прогоном шагов 2–6 без одного фильтра — система показывает, сколько кандидатов добавится.

| Вызов | Назначение |
| --- | --- |
| `POST /positions` | Позиция из потребности → разобранные поля |
| `POST /positions/{id}/shortlists` | Новая версия подборки с объяснениями |
| `GET /candidates?filters` | Банк кандидатов с фильтрами |
| `GET /positions/{id}/relaxations` | Что ослабить и сколько кандидатов добавится |

События: `profile.updated`, `grade.confirmed`, `position.created` → пересчёт эмбеддингов и кэша выдачи.

### Подключение по каналам

- **cloud.ru.** OpenAI-совместимый API — используем стандартный OpenAI SDK с адресом и ключом cloud.ru. Поддержку `tools` и `response_format` с JSON-схемой для GigaChat 3.5 Ultra проверяем при подключении; если строгой схемы нет — схема в промпте, а шлюз валидирует ответ и повторяет запрос.
- **Свой vLLM.** Карточка GigaChat 3.5 Ultra на Hugging Face описывает запуск в vLLM со своим парсером вызовов функций (`--tool-call-parser gigachat35`). Для Lightning — запуск по инструкции на её карточке; vLLM умеет генерацию по JSON-схеме, поэтому структурированный вывод для разбора резюме гарантирован на уровне сервера.
- **API Сбера (эмбеддинги).** Адрес [https://api.giga.chat](https://developers.sber.ru/docs/ru/gigachat/api/authorization); ключ авторизации обменивается на токен запросом `POST https://ngw.devices.sberbank.ru:9443/api/v2/oauth` с `scope` (`GIGACHAT_API_PERS`, `GIGACHAT_API_B2B` или `GIGACHAT_API_CORP`), токен живёт 30 минут; нужен корневой сертификат НУЦ Минцифры. Здесь же доступны [кэширование контекста](https://developers.sber.ru/docs/ru/gigachat/guides/keeping-context) по `X-Session-ID` и [пакетный режим](https://developers.sber.ru/docs/ru/gigachat/guides/batches) — пригодятся для массовой переиндексации эмбеддингов.

### Ограничения

- **3.5 Reasoning пока без бизнес-API.** Агент на приёмке задач работает на 3.5 Ultra; когда Reasoning станет доступна, весь банк задач перепроверяется более сильным агентом.
- **Квоты cloud.ru** в наших источниках не описаны — проверяем при подключении. Очередь с приоритетами в шлюзе нужна в любом случае.
- **[Потоки API Сбера](https://developers.sber.ru/docs/ru/gigachat/limitations):** физлицу — один, юрлицу — 10 по умолчанию. Для эмбеддингов этого достаточно, для генерации мы этот канал не используем.
- **Свой запуск 3.5 Ultra** на хакатоне нереален — нужен кластер. На своём сервере держим только Lightning.
- **Отказы на темах безопасности.** Модели могут отказываться обсуждать атаки; задачи AppSec прогоняем заранее и формулируем со стороны защиты.

### Стоимость

| Канал | Цена |
| --- | --- |
| GigaChat 3.5 Ultra на cloud.ru | 96 ₽ за 1 млн входных токенов, 289 ₽ за 1 млн выходных |
| GigaChat 3.1 Lightning на своём сервере | Только аренда видеокарты |
| Эмбеддинги в API Сбера, юрлица | 0,014 ₽ за 1000 токенов синхронно, 0,007 ₽ асинхронно |

Оценщик в основном читает (условие, рубрика, решение, журнал) и мало пишет (вердикты), поэтому его стоимость определяется в первую очередь ценой входных токенов.

### Что делает LLM Gateway

1. Даёт сервисам один OpenAI-совместимый интерфейс и маршрутизирует: сценарий → модель → канал (cloud.ru, свой vLLM, API Сбера).
2. Хранит ключи каналов; для API Сбера получает и заранее обновляет токен.
3. Держит очередь с приоритетами: ассистент и «заказчик» (кандидат ждёт) → оценщик → фидбэк → приёмка задач → пакетные работы.
4. Валидирует ответы по JSON-схеме, повторяет при ошибке, обрабатывает отказы модели.
5. Переключает канал при сбое: например, разбор резюме уходит с Lightning на 3.5 Ultra.
6. Пишет журнал `LLMCall` — модель, канал, версия промпта, токены, стоимость — и следит за бюджетом токенов на попытку кандидата и на задачу при приёмке.

| Зависимость от cloud.ru | Флагманская модель доступна по API только там; квоты нам заранее неизвестны | Очередь с приоритетами в шлюзе; разбор данных и «заказчик» — на своём Lightning; при сбое шлюз переключает сценарии Lightning на 3.5 Ultra и обратно |
| Нет видеокарты под Lightning | Без неё свой канал не поднять | Временно все сценарии через 3.5 Ultra на cloud.ru; дороже, но архитектура не меняется |
| Отказы модели на темах безопасности | Задачи AppSec могут не генерироваться или ломать ассистента | Прогон банка AppSec заранее; формулировки со стороны защиты, а не атаки |
| Разброс и предвзятость оценщика | Грейд плавает между прогонами, длинные ответы оцениваются выше | Бинарные критерии с цитатой, 3 прогона, нижний балл при расхождении, запрет поощрять объём в инструкции |
| Инъекции в решении против оценщика | Кандидат пишет в решении текст для оценщика | Известный риск; после хакатона — изоляция решения в промпте и тесты на атаки |
| Утечка задач через фидбэк | Разбор с эталоном разойдётся между кандидатами | Рекомендации на уровне навыка, без эталона; проверка опоры на факты |
| Субъективные веса графа смежности | Смежные кандидаты могут ранжироваться выше или ниже, чем заслуживают | Стартовые веса от экспертов, затем дообучение на исходах; задача в целевом домене поднимает соответствие домена до полного |
| Стоимость оценки на 3.5 Ultra | Три прогона на каждую задачу | Оценщик почти не пишет, а входные токены втрое дешевле выходных; асинхронная обработка всего, чего не ждёт пользователь |
