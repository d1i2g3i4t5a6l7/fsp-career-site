# Платформа подбора ИТ-специалистов ФСП — спецтрек хакатона

Платформа «ФСП Карьера» (рабочее название): кандидат подтверждает грейд рабочими задачами с разрешённым ИИ, работодатель находит его по подтверждённому профилю и сам отправляет приглашение с обязательной вилкой. Отклик кандидата на вакансию — дополнительный сценарий.

## Критерии оценки ТЗ

Новая механика подбора 35% · тестирование и категоризация 25% · интерфейс 10% · презентация 10% · техническая проработка 7% · доп. функционал 7% · полнота и документация 6%. Первые два — 60% оценки, на них и тратим время.

## Принятые решения — не пересматривать без согласования

### Тестирование и грейд

- ИИ в тестировании **разрешён официально**: кандидат работает со встроенным ИИ-ассистентом сайта.
- Уход со вкладки во время теста **запрещён и отслеживается**: любой уход отмечается в результате, попытка помечается, решает человек. Аннулировал — грейд, полученный попыткой, снимается, тесты кандидата заморожены на 30 дней.
- Никаких вопросов на знание и задач «что выведет этот код», никаких адаптивных тестов по IRT.
- Три типа задач: поиск бага, системный дизайн, фича по абстрактному ТЗ. Тип задачи ≠ грейд: у каждого типа свои уровни.
- Тест на грейд — **одна задача на 30 минут** (пока).
- В задаче 1…N файлов (для демо 2–3) и тесты: кнопка «Запустить тесты» прогоняет их. Ассистент предлагает правки, кандидат принимает или отклоняет.
- Грейды: Стажёр, Junior, Middle, Senior. Направления — как на сайте: Backend, Frontend, Mobile, Data / ML, DevOps, QA, Инф. безопасность.
- В задаче есть скрытые ограничения, ломающие очевидный подход; часть их раскрывает бот-«заказчик» только на уточняющий вопрос.
- Рубрика: 8–15 критериев с весами, проверяет решения в условиях ограничений, а не наличие разделов («оценил объём разметки в бюджет», а не «предусмотрел сбор данных»). Плюс 2–3 критерия процесса по журналу сессии.
- Кандидат работает со **встроенным ассистентом**, сессия пишется автоматически; загружать лог не нужно.
- Вердикт о грейде выносит **LLM** и собирает отчёт по критериям: по каждому критерию вердикт с цитатой (без цитаты не засчитывается), 3 прогона, по критерию — большинство; если прогоны дают разный грейд — берётся нижний.
- Балл теста — нормализация к шкале 0–100, округление вверх.
- Пункт «проверял работу ассистента» засчитывает сайт по журналу действий, без ИИ: отклонил правку ассистента, поправил принятую или запустил тесты после неё.
- На демо кандидат не должен видеть внутреннюю кухню: ограничения песочницы, служебные файлы и метки, внутренние номера и тексты ошибок.
- Условие задачи пишется для человека: «Ситуация», «Что нужно сделать», «Условия» — без внутренней кухни. На странице теста рядом с ним — «Что оценивается», «Что можно делать» и «Важно» про очередь GigaChat.
- Отчёт и оценку видят люди («Проверка оценок» у работодателя) и при необходимости исправляют вердикты по критериям: итог теста — по исправленным, поменялся итог — меняется и грейд. Оценка ИИ сохраняется рядом.
- Эксперты платформы проверяют задачи перед банком. Приёмка задачи в банк: структура → исполнимость → агент без человека в 3 прогонах **не набирает порог** → калибровка оценщика → эксперты решают в лимит времени и задают пороги грейдов.
- Не подтвердил грейд — сразу доступны задачи уровнем ниже; тот же уровень — через 30 дней; смена грейда не чаще раза в 90 дней. Принудительного понижения грейда нет (требование ТЗ).

### Подбор и контакт

- Грейд **не понижается за смену домена или специализации**.
- Рейтинг кандидата — как на сайте (`frontend/public/data.js`, функция `score`): тест 45 · совпадение стека 25 · достижения ФСП 15 · активность 10 · экспертная проверка 5, всего 100. У каждого слагаемого — строка объяснения.
- Поиск — как на сайте: подборка под потребность по категориям и банк кандидатов с фильтрами; уточнения не сбрасывают подборку. Регулярные задания от компаний держат профиль свежим.
- Приглашение: вилка «от–до» в ₽ обязательна. Кандидат принимает или отклоняет **с причиной**. Ограничений на число приглашений, ширину вилки и срок ответа нет.
- Контакты раскрываются только после принятия приглашения или при отклике кандидата. Что видно в карточке до принятия и условия отклика — нерешённые вопросы (`docs/04-open-questions.md`).
- Фидбэк кандидату и отчёт работодателю собираются **только из вердиктов по критериям**, каждый пункт ссылается на `criterion_id`. Кандидату — без эталона, работодателю — без текста задачи.
- Вход — тестовые аккаунты, зашитые в сайт. «ФСП ID» и реестр достижений — имитация. Отсутствие истории ФСП не штрафуется.

### Модели — только национальные, поколение GigaChat 3.x

- GigaChat 3.5 Ultra через OpenAI-совместимый API cloud.ru: генерация задач, агент без человека, ассистент, оценщик, фидбэк.
- GigaChat 3.1 Lightning на своём vLLM: разбор резюме, вакансий и потребностей, бот-«заказчик», автопроверки задач. Нет видеокарты — эти сценарии временно идут через 3.5 Ultra.
- EmbeddingsGigaR через API Сбера (api.giga.chat) — эмбеддинги профилей и позиций в pgvector.
- GigaChat 2 не используем. Когда откроют API GigaChat 3.5 Reasoning — переводим на неё агента приёмки и перепроверяем банк.
- Все вызовы — только через LLM Gateway: маршрутизация по каналам, очередь с приоритетами, валидация ответа по JSON-схеме, журнал `LLMCall`.

### Вне MVP и известные риски

- (*) Отзывы компаний после собеседования — задел на будущее. Если вводить: абсолютный вопрос, учёт строгости компании, одиночный отказ ничего не меняет, грейд не понижается.
- Защита от фиктивных вакансий и интеграция с ATS — только концепция в документации.
- На хакатоне не решаем: утечку открытых задач, инъекции в решении против LLM-оценщика.

### Отвергнутые идеи — не предлагать снова

Тесты на знание и IRT; детекция ИИ-списывания (уход со вкладки — отдельное правило, его отслеживаем); очные проверки под наблюдением; понижение грейда за проваленное собеседование или смену домена; GigaChat 2; граф смежности доменов с весами; ограничения на приглашения (квоты, лимиты ожидающих, ширина вилки, срок ответа); Keycloak на хакатоне; перевод фронта на TypeScript.

## Архитектура кратко

Логические сервисы (подробно — `docs/02-architecture.md`): Identity, Profile, Taxonomy, FSP Adapter · Task Bank, Task QA, Assessment, Workspace, Sandbox Runner, Grading, Feedback · Matching, Vacancies, Drafting, Notifications · LLM Gateway.

На хакатоне собираем в контейнеры:

1. `core-api` — модульный монолит: Profile, Taxonomy, Task Bank, Assessment, Matching, Vacancies, Drafting, FSP Adapter.
2. `ai-worker` — фоновые задачи: Task QA, Grading, Feedback, пересчёт эмбеддингов.
3. `workspace` — WebSocket-сессии кандидата: ассистент, «заказчик», журнал.
4. `llm-gateway` — отдельно: все сервисы делят его очередь и лимиты.
5. `runner` — песочница для кода без сети.

Плюс `web` (сайт), PostgreSQL + pgvector, Valkey, vLLM с Lightning. Границы модулей внутри `core-api` совпадают с сервисами — разнести позже механически.

Сейчас (стенд — `compose.yaml` в корне, хостинг пока только локальный): `web` + `workspace` + `runner` + `postgres`. `web` — сайт из `frontend/`, собирается Vite, отдаётся nginx, порт 8080; к бэкенду пропускает только адреса, которыми пользуется сайт, и Swagger (`/api/workspace/docs`), служебное — только `localhost:8010`; общий пароль на сайт — `SITE_PASSWORD`. В `workspace` пока живут и Task Bank, Assessment, Grading, генерация задач, и LLM Gateway — в одном процессе, фоновые задачи на asyncio. Поэтому он строго в одной копии с `--workers 1`. `llm-gateway` выносим отдельно, когда LLM понадобится `core-api`: иначе лимит потоков GigaChat поделится между процессами. `ai-worker` и Celery — когда фоновой работы станет больше, чем тянет один процесс.

Стек: Python, FastAPI, SQLAlchemy, Alembic, Pydantic · Celery + Valkey · PostgreSQL + pgvector · песочница — свой `runner` с API Piston: без сети и без privileged, работает в любом Docker; сам Piston подключается той же настройкой · pdfplumber, WeasyPrint · фронт: React 18 + Vite, обычный JavaScript (`frontend/`). Лицензии: Valkey вместо Redis, MinIO не берём (AGPL) — файлы на хакатоне в Docker-томе за интерфейсом хранилища.

## Валидация в MVP

- Тестирование: агент без человека не проходит задачи; согласие LLM-оценщика с экспертами (κ, ICC); стабильность грейда на двух параллельных задачах; разброс оценки одного решения между прогонами; «ИИ-атака» — агент проходит путь кандидата.
- Подбор: Precision@10 против поиска по резюме (BM25) на 12 вакансиях и 600 синтетических кандидатах; агентная симуляция рынка «драфт против отклика».
- Результаты — на странице `/validation/report` и в документации.

## Среда разработки

- Облачная среда разработки может не видеть api.giga.chat и cloud.ru. Поэтому у LLM Gateway два режима: `live` и `stub` (заглушка, отдающая валидные по тем же JSON-схемам ответы). Живые вызовы проверяем на машине команды.
- Ключи GigaChat и cloud.ru — только в `.env`, никогда в git и не в чат.

## Как работать

- Отвечать по-русски, коротко и по делу.
- Это хакатон: прагматично, без оверкилла. Всё, что не даёт баллов по критериям, откладывать и помечать как «после хакатона».
- Перед изменением любого решения из этого файла — спросить.
- Логику бэкенда менять только по согласованию.
- Фронт: логику и вид без согласования не менять; стиль сайта соблюдать строго. Каждая правка — запись в `docs/03-frontend-changes.md`: файл, номера строк, зачем, как откатить (без кода целиком).
- Порядок: сначала сквозной путь (регистрация → задача → оценка → грейд → поиск → приглашение) на заглушке LLM, потом глубина.

## Подача для жюри

Не говорить «тесты не работают». Формулировка: «Закрытые тесты знаний не работают — это показали LinkedIn и опыт рынка. Мы сохранили тестирование, но изменили, что оно измеряет: работу с ИИ на реальной задаче, как это делают Canva и Meta».
