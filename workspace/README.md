# workspace — рабочее место кандидата

Сессия решения задачи: таймер, файлы, ИИ-ассистент, тесты в песочнице и журнал всех действий для оценки.

Ассистент читает файлы и запускает тесты сам, а правки только **предлагает**: кандидат видит дифф и принимает или отклоняет. Принятые, отклонённые и ручные правки пишутся в журнал.

Все вызовы моделей идут через шлюз `app/llm`. У каждого канала свой лимит одновременных запросов, лишние ждут в очереди. После 429 весь канал ставится на паузу. Ненастроенный или упавший канал заменяется запасным.

## Запуск

Стенд целиком (workspace, песочница, Postgres) — `docker compose up -d --build` из корня репозитория, см. [README](../README.md). Ниже — запуск для разработки.

```bash
python -m venv .venv
.venv/Scripts/pip install -r requirements-dev.txt   # Linux/macOS: .venv/bin/pip
cp .env.example .env
.venv/Scripts/uvicorn app.main:app --reload --port 8010
```

Swagger: http://localhost:8010/docs. По умолчанию `LLM_MODE=stub`: ассистент — заглушка без сети, отвечает по ключевым словам («исправь», «запусти тесты», «файлы»). Для реальной модели укажите `LLM_MODE=live` и ключ в `.env`.

Тесты: `.venv/Scripts/pytest`. На Postgres: `TEST_DATABASE_URL=postgresql+asyncpg://user:pass@localhost/test_db pytest` — база очищается перед каждым тестом.

## API

| Вызов | Что делает |
| --- | --- |
| `POST /tasks/generate` `{categories, grades, type?, brief?, time_limit_min?}` | Сгенерировать задачу в банк (в фоне) |
| `GET /tasks/generations/{id}` | Статус генерации: попытки, что не прошло проверки, id задачи |
| `GET /tasks?category=&grade=&status=` | Банк задач; `status=review` — очередь эксперта |
| `GET /tasks/{id}` | Задача целиком: файлы, эталон, критерии, пороги |
| `POST /tasks/{id}/review` `{expert, approved, comment}` | Эксперт проверил задачу на решаемость: одобрил или отклонил |
| `POST /attempts` `{candidate_id, category, level}` или `{candidate_id, task_id, category?, level?}` | Старт теста на категорию и грейд: таймер, копия файлов задачи. Без `task_id` — случайная подходящая задача, сначала из нерешённых |
| `GET /attempts/{id}` | Состояние: условие, «что оценивается», файлы, правки, лента чата, счётчики, остаток времени |
| `POST /attempts/{id}/assistant` `{text}` | Сообщение ассистенту → `{reply, edits}` |
| `POST /attempts/{id}/edits/{edit_id}/accept` · `/reject` `{reason}` | Решение по правке ассистента |
| `PUT /attempts/{id}/files` `{path, content}` | Ручная правка из редактора |
| `POST /attempts/{id}/tests` | Запуск тестов |
| `POST /attempts/{id}/submit` | Сдать решение, проверка стартует в фоне |
| `GET /attempts/{id}/result` | Результат теста: балл из 100, вердикты по критериям с цитатами, итог |
| `POST /attempts/{id}/focus` `{left}` | Кандидат ушёл со вкладки теста (`true`) или вернулся (`false`). Уход запрещён: отмечается в результате |
| `POST /attempts/{id}/review` `{reviewer, annul, comment, verdicts?}` | Решение человека по попытке: подтвердить оценку ИИ; `verdicts` — исправить вердикты по критериям (итог и грейд — по исправленным); `annul=true` — аннулировать (грейд, полученный попыткой, снимается, тесты кандидата заморожены на 30 дней). Один раз |
| `GET /reviews` | Очередь «Проверки оценок»: сданные тесты с готовой оценкой ИИ; помеченные за уход со вкладки и ещё не решённые — первыми |
| `POST /attempts/{id}/grade` | Перепроверить завершённую попытку |
| `GET /candidates/{id}/grade?category=` | Экран «Грейд и тесты»: грейд, балл, «доступно с», какие тесты доступны |
| `GET /candidates/{id}/attempts` | История тестов: балл, итог |
| `GET /attempts/{id}/events` | Журнал сессии |
| `WS /attempts/{id}/ws` | Живой поток: статус ассистента, текст по мере генерации, события журнала |

Ошибки: 400 — неверный запрос, 404 — нет попытки или задачи, 409 — ассистент ещё отвечает, попытка закрыта или правка устарела, 502 — модель недоступна.

### Что приходит по WebSocket

Фронт держит WS открытым, отправляет сообщение через `POST /assistant` и рисует ответ из потока:

```text
{"type": "assistant.status", "state": "started"}
{"type": "assistant.status", "state": "generating"}
{"type": "assistant.status", "state": "tool", "tool": "read_file", "path": "dedup.py"}
{"type": "event", "event": {"type": "edit.proposed", "payload": {"edit_id": 3, "diff": "…"}}}
{"type": "assistant.delta", "text": "Предложил правку"}             ← куски склеивать по порядку
{"type": "event", "event": {"type": "assistant.message", "payload": {"text": "…", "edit_ids": [3]}}}
{"type": "assistant.status", "state": "idle"}
```

Итоговый `assistant.message` содержит весь ответ целиком, его текст заменяет склеенные куски. Тот же ответ возвращает и `POST /assistant`.

## Проверка и грейд

Проверку запускает сдача решения или конец времени. Фоновый сторож раз в `GRADING_POLL_S` секунд закрывает просроченные попытки и отправляет на проверку всё непроверенное, в том числе после перезапуска сервиса.

1. Автотесты задачи прогоняются на итоговых файлах. Критерии с `"check": "tests"` засчитываются по этому прогону сами, без судьи. Критерии с `"check": "verified"` («проверял работу ассистента») — по журналу, тоже без судьи: засчитан, если кандидат отклонил правку ассистента, поправил принятую вручную или запустил тесты после неё; доказательство — строки журнала.
2. Судья (сценарий `grader`, `ROUTE_GRADER`) получает итоговые файлы, журнал сессии и вывод тестов. По каждому остальному критерию он ставит `yes`, `partial` или `no` с цитатой. Прогонов `GRADER_RUNS`, по умолчанию 3.
3. Постобработка:
   - цитата должна быть взята из материалов, а не пересказана: куски цитаты ищутся в файлах, журнале и выводе тестов, к склейке строк, другим кавычкам и паре слов судьи вокруг проверка терпима; не нашлась — критерий не засчитывается;
   - `partial` у критерия без `partial_points` считается как `no`;
   - итог по критерию — большинство прогонов.
4. Баллы — сумма по критериям, пересчитанная в 100 с округлением вверх. Тест на грейд пройден, если взят порог этого грейда: баллов из 100 не меньше `min_score` и все его `required`-критерии `yes`. Если прогоны разошлись, засчитывается нижний результат (`unstable: true`).
5. Результат пишется в `gradings`, сырые вердикты каждого прогона — в `criterion_verdicts`. По WebSocket приходит событие `grading.completed`.

Рубрика в задаче:

```json
"rubric": {
  "criteria": [
    {"id": "dedup", "text": "Повторное событие не учитывается", "points": 5},
    {"id": "new-test", "text": "Добавлен новый тест", "points": 3, "partial_points": 1},
    {"id": "verified-ai", "text": "Проверял правки ассистента", "points": 2, "kind": "process"}
  ],
  "thresholds": [
    {"grade": "junior", "min_score": 50, "required": ["dedup"]},
    {"grade": "middle", "min_score": 70, "required": ["dedup", "new-test"]}
  ]
}
```

Порог на каждый грейд задачи; у задачи на один грейд — один порог приёма. Во время решения кандидат рубрику не видит, ему показывается только `assessed` («Что оценивается»).

## Итог теста и грейд

1. Итог теста — оценка LLM-судьи после постобработки: `ai_score` из 100, тест на грейд пройден, если взят порог этого грейда. Отчёт видят люди и при необходимости корректируют; задачи до банка проверяет эксперт (см. ниже).
   Грейды — как на сайте: `intern` (Стажёр), `junior`, `middle`, `senior`. Направления — как на сайте: Backend, Frontend, Mobile, Data / ML, DevOps, QA, Инф. безопасность; принимаются по id (`data`) или названию (`Data / ML`), другие — ошибка.
2. Тест пройден → грейд кандидата в категории меняется на уровень теста сразу после оценки, следующая смена — через `GRADE_CHANGE_COOLDOWN_DAYS` (90). Не пройден → грейд не трогаем, принудительного понижения нет.
3. Какие тесты можно начать (иначе `POST /attempts` отвечает 409 с причиной):
   - один тест за раз;
   - нельзя тест на свой текущий грейд;
   - смена грейда — раз в 3 месяца;
   - после непройденного теста уровень ниже доступен сразу, тот же уровень — через `SAME_LEVEL_RETRY_DAYS` (30);
   - пока предыдущий тест на этот уровень проверяется, повторить его нельзя;
   - попытку аннулировали — все тесты кандидата заморожены на `ANNUL_FREEZE_DAYS` (30).
4. Уход со вкладки во время теста запрещён. Сайт сообщает о каждом уходе и возврате (`POST /attempts/{id}/focus`), любой уход — нарушение. В результате — `violations` (сколько раз и сколько секунд) и `needs_review`: попытку помечаем, решает человек (`POST /attempts/{id}/review`). Аннулировал — грейд, полученный этой попыткой, снимается и возвращается прежний подтверждённый; тесты кандидата заморожены на 30 дней. Засчитал — всё остаётся как есть.
5. Отчёт ИИ проверяет человек на странице «Проверка оценок» (`GET /reviews`, `POST /attempts/{id}/review`): подтверждает, исправляет вердикты по критериям или аннулирует. Исправил — баллы и пороги пересчитываются по рубрике, итог теста — по исправленным вердиктам (`final`, `criteria`, `thresholds`, `correction`), а оценка ИИ остаётся в `ai_score` и `ai_verdict`. Поменялся итог «пройден / не пройден» — вслед за ним меняется грейд: стал пройденным — грейд становится уровнем теста (если позже кандидат не получил грейд другим тестом), перестал — возвращается прежний. Критерии по автотестам не исправляются. В разборе по каждому критерию есть `said` — что судья сказал в каждом прогоне, и `unconfirmed` — сколько раз его «да» или «частично» не подтвердилось цитатой и потому не засчитано.

## Задачи и их генерация

У задачи есть категории (`["Data / ML"]`) и грейды (`["middle", "senior"]`). Тест на категорию и грейд выдаёт любую подходящую задачу. Попытка запоминает, на какую категорию и грейд был тест.

`POST /tasks/generate` (сценарий `task_gen`, `ROUTE_TASK_GEN`):

1. Модель пишет черновик: условие, стартовые файлы и тесты unittest (`test_*.py`), эталон, критерии и пороги по грейдам. Тип — `bug`, `feature` или `design` (дизайн — с Middle); если не задан, выбирается случайно. Время по умолчанию — 30 минут.
   Формат ответа — блоки: `=== META ===` с JSON (условие, критерии, пороги), затем `=== FILE files/… ===` и `=== FILE reference/… ===` с кодом как есть. Код в JSON-строках GigaChat ломал при экранировании.
2. Платформа сама правит мелочи, на которые жалко тратить попытку:
   - вырезает из стартового кода задачи на баг комментарии-подсказки (`# BUG: …`);
   - оставляет автоматическим (`check=tests`) только один критерий.
3. Платформа проверяет:
   - пороги стоят ровно на запрошенные грейды, критерии и пороги согласованы;
   - у `bug` и `feature` есть тесты и эталон, эталон не меняет тесты;
   - тесты на стартовом коде падают, но не из-за синтаксиса или импортов;
   - тесты на эталоне проходят.
4. Не прошло — модель получает список проблем (с выжимкой ключевых ошибок тестов) и присылает исправленный черновик, до `TASK_GEN_FIX_ATTEMPTS` раз (по умолчанию 3). Битый ответ — тоже неудачная попытка, а не падение.
5. Прошло — задача с номером `V1-XXXX` попадает в банк со статусом `review`. Что исправлено и что не прошло — в отчёте `GET /tasks/generations/{id}`.
6. Эксперт проверяет задачу на решаемость: может прорешать её сам (`POST /attempts` с её `task_id`) и решает `POST /tasks/{id}/review`. Одобренная (`published`) выдаётся кандидатам, отклонённая (`rejected`) — нет, даже по id. Решение можно поменять — например, снять уже опубликованную задачу.

На живом GigaChat обычная задача («Data Science, middle, отчётность магазина») собирается за 1–2 минуты с 2–3 попыток. Тяжёлые темы, которые плохо укладываются в один процесс без сети (например, распределённый лимитер), могут не собраться за все попытки — тогда генерацию стоит повторить или упростить тему.

Файл запуска тестов (`run_tests.py`) кладёт платформа. Код задач — Python и стандартная библиотека. Если в песочнице есть ещё пакеты (`numpy`, `pandas`…), перечислите их в `SANDBOX_PACKAGES`, и модель будет их использовать.

Задачи в банке из репозитория — папки с `task.json`, `files/`, `reference/`: `tasks/placeholder-dedup` (V1-7C2A, дедупликация платежей, баг, все грейды) и `tasks/payment-rate-limiter` (V1-4E9B, ограничитель запросов для платёжного API, Middle и Senior, три файла).

## Песочница

`SANDBOX=local` запускает код кандидата прямо на машине — это только для разработки. На стенде — `SANDBOX=piston`: песочница по API Piston. В docker compose это наш контейнер [`runner/`](../runner/server.py) без сети, `PISTON_URL=unix:/run/runner/runner.sock`. Подойдёт и сам [Piston](https://github.com/engineer-man/piston) (`PISTON_URL=http://…:2000`), но ему нужен privileged-контейнер, `PISTON_RUN_TIMEOUT=20000` и `PISTON_OUTPUT_MAX_SIZE=65536`: по умолчанию у него 3 с на запуск и 1 КБ вывода.

## Банк задач в репозитории

Сгенерированные задачи живут в БД. `python scripts/export_tasks.py` выгружает одобренные в `tasks/<id>/`, оттуда они загружаются при старте на любой машине. Папки, которые уже есть, не перезаписываются (`--update` — перезаписать).
